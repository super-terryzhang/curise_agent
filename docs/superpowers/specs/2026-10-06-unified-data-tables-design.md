# 统一数据表管理第一轮设计

日期：2026-10-06。

状态：用户已确认统一方向与第一轮边界；本文是进入实施计划前的正式设计。它扩展现有 `0035_custom_data_tables` 本地成果，不表示功能已经合并、部署或迁移生产。

## 目标与成功标准

用户只理解一个概念：**数据表**。设置中心的同一页面列出产品、供应商、订单和用户新建的数据表；用户可以选择已有表，或创建新表，不再需要理解“自定义数据表／非自定义数据表”的区别。

产品、供应商和订单的核心字段保持原有业务数据来源及校验。核心字段在统一页面中可查看但结构锁定，核心内容通过现有业务页面修改；管理员可以为这些表添加扩展字段，授权用户可以直接维护扩展字段值。新增扩展字段不要求再次执行数据库迁移或重新部署。

第一轮完成后，用户应能在本地完成：进入“数据表管理” → 打开产品、供应商或订单 → 看见锁定的核心字段 → 新增扩展字段 → 为现有记录填写扩展内容 → 查看修改历史；同时仍可创建并维护普通数据表。

## 设计原则

1. **统一概念，不伪装底层事实。** 页面只叫“数据表”，但字段上的锁定状态必须清楚，不能让用户点击后才发现不能修改。
2. **一个核心数据来源。** 不复制产品、供应商或订单业务字段到动态表，避免两份名称、状态或港口互相漂移。
3. **不绕过原业务规则。** 价格区间、产品关系、PO 状态、商品匹配和询价仍由现有页面及服务负责。
4. **扩展能力独立。** 扩展字段定义和值由统一数据表模块负责，失败不能留下半条数据，也不能改变核心记录。
5. **渐进交付。** 第一轮先完成三张核心表的扩展字段；跨系统表关联、通用页面编辑核心字段和批量扩展值更新以后单独设计。

## 已选择的技术方案

采用“统一目录 + 系统表适配器 + 扩展值锚点”。不采用以下两种方案：

- 不把核心记录复制成普通动态记录；复制会形成两个数据来源，并要求持续同步所有新增、修改和归档入口。
- 不分别给 `products`、`suppliers`、`v2_orders` 增加 JSONB 自定义列；这种做法会复制字段、校验、历史和查询代码，下一张核心表还要再次迁移。

统一目录继续使用 `v3_data_tables`。用户创建的表走现有动态记录实现；产品、供应商和订单由只读适配器从原 ORM 表读取核心字段，并把扩展值与结果合并。扩展值仍存入 `v3_data_records.values`，不会写入核心表。

## 数据结构

新增迁移 `0036_unified_data_tables`，在尚未上线的 0035 后执行：

### `v3_data_tables`

- 新增 `table_kind`：`user` 或 `system`，默认既有表为 `user`。
- 新增可空且唯一的 `system_key`。
- 迁移以固定 UUID 幂等创建三张启用表：`products`、`suppliers`、`orders`；操作人使用内部系统编号，不能依赖生产必然存在某个用户。
- 系统表不能重命名、归档或恢复；用户表保持现有行为。

### `v3_data_records`

- 新增可空 `source_record_id` 字符串，并建立 `(table_id, source_record_id)` 唯一约束。
- 用户表记录保持 `source_record_id = NULL`，现有 UUID、关联、唯一值和历史行为不变。
- 系统表的扩展值记录只保存扩展字段值及独立 revision；`source_record_id` 指向原产品、供应商或订单主键。
- 没有扩展值的核心记录不提前创建空锚点。第一次保存扩展值时，在同一事务中验证核心记录仍存在、创建锚点、校验字段、写值并追加历史。
- 统一接口返回字符串形式的记录标识。用户表仍是 UUID 字符串；系统表使用原主键字符串。服务层根据 `table_kind` 解析，不能把任意字符串传入 SQL。
- 系统记录保存请求携带客户端生成的 `request_id`。首次保存以它作为内部锚点 UUID；响应丢失后，相同请求编号、来源记录、操作人和规范化内容可安全返回已有结果，不同内容或不同请求争抢同一来源记录返回 409。

### 核心字段

核心字段定义保存在代码中的系统表注册表，不作为 `v3_data_fields` 可编辑行。每个核心字段具有固定 ID、显示名、类型、读取函数和锁定标记；前端与历史使用固定 ID，改文案不能改变身份。

`v3_data_fields` 中属于系统表的行全部是用户新增的扩展字段。接口把核心字段描述与扩展字段合并后返回，并明确提供：

- `source = core | extension`
- `locked = true | false`
- `system_key`（仅核心字段使用）

核心字段不接受修改、排序、归档或恢复接口。系统表扩展字段第一轮支持文本、数字、日期、日期时间、单选、多选和是／否；暂不提供关联记录类型。用户创建表继续支持现有八种类型及表间关联，目标表选择器第一轮排除系统表。

## 系统表适配器

后端新增独立注册表和三个适配器，每个适配器只负责：核心字段定义、总数、分页搜索、按主键读取、记录是否存在、显示名称和原业务页面链接。适配器不提供核心字段写入。

第一轮展示字段：

| 数据表 | 核心字段摘要 | 原业务入口 |
|---|---|---|
| 产品 | 英文名、日文名、产品代码、供应商、国家、类别、港口、单位、品牌、状态 | `/dashboard/data/products/{id}` |
| 供应商 | 名称、国家、联系人、邮箱、电话、地址、付款方式、付款条件、状态 | `/dashboard/data?tab=suppliers&edit={id}` |
| 订单 | PO 编号、船名、装船日期、目的港、处理状态、进入系统时间 | `/dashboard/orders/{id}` |

关系名称通过批量查询读取，不在逐行循环中访问数据库。系统表记录第一页和搜索使用原表的受控 SQL 查询；搜索只覆盖适配器声明的文本字段，参数绑定，最大每页 100 条。第一轮不承诺按扩展字段筛选或排序。

## 接口行为

保留 `/api/data-tables` 前缀和现有用户表接口，响应扩展 `table_kind`、`system_key`、字段来源和原业务链接。

- 表列表和详情：统一返回系统表及用户表；系统表记录数来自核心表，字段数是核心字段与启用扩展字段之和。
- 字段列表：系统表返回锁定核心字段 + 可配置扩展字段；用户表行为不变。
- 记录列表和详情：系统适配器读取核心记录，再按当前页 `source_record_id` 批量合并扩展值；不能为每一行单独查询。
- 系统记录保存：请求只接受启用扩展字段 ID，携带 `expected_revision` 与 `schema_version`；首次保存 revision 为 0，之后必须精确匹配当前扩展 revision。
- 系统记录归档／恢复：统一页面不提供，接口明确拒绝并引导前往原业务页面。
- 修改历史：系统表显示扩展字段结构和扩展值的历史；核心字段在原业务历史中查看，不伪装成统一历史已经覆盖全部业务修改。

未知字段、提交核心字段、核心记录已不存在、结构版本过期和扩展记录版本冲突均返回稳定中文错误与具体字段。保存失败保留页面输入；网络结果不确定时保留同一请求身份，先重新读取核对，不自动创建第二个锚点。

## 页面与交互

### 数据表列表

- 页面标题改为“数据表管理”，说明为“选择已有数据表，或创建新的数据表并配置字段”。
- 系统表和用户表位于同一张列表，不增加“自定义／非自定义”类型列。
- 每行统一显示表名、状态、字段数、记录数、更新时间和“打开”。
- 系统表不显示“修改表信息、归档”按钮；用户表保留这些操作。
- “新建数据表”在页头保持主操作。创建后的表立即出现在同一列表。
- 删除“独立于产品、订单”的旧说明和所有面向用户的“自定义数据表”措辞。

### 表详情

统一保留“字段配置、数据记录、修改历史”三个标签。系统表页头提示：“核心字段受保护；新增字段可在此配置和维护。”用户表不显示这条说明。

字段表中，核心字段使用统一的锁定标识和只读状态，不显示修改、排序或归档操作；扩展字段保持现有操作。新增字段表单在系统表中隐藏“关联记录”类型，并解释第一轮边界。

系统记录编辑采用上下两区：

1. “核心信息”只读展示适配器声明字段，并提供“前往产品／供应商／订单页面修改”。
2. “扩展信息”只显示管理员新增的字段，授权用户在此填写和保存。

没有扩展字段时，不显示空白保存表单；管理员看到“新增字段”，普通用户看到“尚未配置扩展字段”。用户表继续使用现有完整动态表单。

系统表的数据标签不显示动态表的“启用／归档记录”筛选和记录归档按钮；核心业务状态作为锁定字段正常展示。系统记录是否可见以及停用记录如何展示，沿用对应产品、供应商或订单查询的现有规则。

## 权限与保护

- Admin／Superadmin 管理表和扩展字段；Employee／Finance 继续按现有 Writer 规则维护扩展值。
- 核心字段是否可编辑仍由原产品、供应商和订单入口各自的权限决定；统一页面不扩大权限。
- 系统表适配器必须接收当前 Actor 并复用原业务读取范围。订单记录、搜索结果、扩展值及记录历史不能因为进入统一页面而向原本无权读取该订单的账号开放；结构历史与记录历史在服务端分开过滤。
- 前端隐藏操作只是体验，后端必须根据 `table_kind` 与字段来源再次拒绝核心结构修改及核心记录归档。
- 系统表注册表只接受固定允许的 ORM 模型和列，不允许客户端提交表名、列名或任意 SQL。
- 结构修改、扩展值、唯一占位和历史继续保持一个事务；核心表在此次事务中只读。

## 兼容性与技术债务边界

- 现有用户创建表、八字段类型、表间关联、归档恢复、筛选和历史行为保持不变。
- 内部环境变量 `CUSTOM_DATA_TABLES_ENABLED` 和 API 路径可暂时保留，避免为用户不可见的命名重复扩大发布风险；页面不再出现该术语。
- 不重做产品详情、供应商编辑或 PO 页面；只提供明确入口。
- 不让扩展字段自动参与产品匹配、价格区间、异常检测、归组、询价、Agent 工具或 Excel 模板。这些接入必须逐项明确业务含义后再实现。
- 第一轮不提供系统表之间、用户表到系统表或系统表到用户表的关联字段；不提供扩展值批量编辑、导入导出和跨字段公式。

## 测试与验收

采用按风险逐步扩大：每个小任务运行针对性测试，适配器与扩展保存接通后运行统一数据表流程测试，稳定候选才运行一次完整回归。

后端必须证明：

- 0035→0036 保留用户表和记录，幂等创建三张系统表且不修改核心业务行。
- 三个适配器数量、分页、搜索、关系名称与详情链接正确，无逐行查询。
- 核心字段结构和核心值不能经统一 API 修改；原业务 API 行为不变。
- 系统记录首次扩展保存、并发 revision、结构版本、唯一值、错误回滚和历史正确。
- 删除或不存在的核心记录拒绝保存扩展值；用户表原有完整路径继续通过。
- 角色、跨表 ID、注入输入和功能关闭状态保持受保护。

前端必须证明：

- 页面只使用“数据表管理／数据表”，列表同时显示三张系统表和用户表。
- 系统表不出现改名或归档操作，核心字段明确锁定，扩展字段可新增和维护。
- 系统记录核心区只读、扩展区可编辑，保存错误保留输入，原业务入口正确。
- 用户表的建表、字段、记录、关联和历史没有回归。
- TypeScript 和生产构建通过。

本地验收使用合成产品、供应商和订单以及独立 PostgreSQL，不复制生产数据。交付时启动本地页面供用户检查；本阶段不合并 main、不推送 GitHub、不迁移生产、不部署。

## 发布影响

生产当前仍为 0034，本分支 0035 尚未上线。最终发布需要按受控方案连续演练并执行 0034→0035→0036，更新精确 schema guard、后端和 Oracle Job 同镜像、再发布前端。迁移只增加动态数据结构、目录标识和三张系统目录行，不改写产品、供应商、订单或价格数据。

回退优先关闭统一数据表入口并使用兼容过渡应用，保留 0035／0036 中用户已录入的扩展数据；不得通过 downgrade 删除表或扩展值。正式发布仍须单独获得授权。
