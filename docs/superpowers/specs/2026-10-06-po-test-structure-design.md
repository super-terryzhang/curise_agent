# PO 流程测试目录与验收设计

日期：2026-10-06。目标是让 PO 八个业务环节各自可验证、连接后可验证，且错误能定位到具体步骤和商品行。系统负责承载这些业务规则，页面能打开、任务正常退出或测试数量增加都不能替代业务结果核对。

本设计落实用户已认可的测试目录方案。范围为当前后端 `v3_backend/` 的测试、样本、验收说明与报告配置；不重建后端、不改生产业务规则、不迁移数据库、不操作生产订单，也不涉及独立 `scheduler/`、`oracle-po-monitor/` 和文件接收项目。

当前状态：目录方向已获用户同意，书面设计待确认；测试代码和目录迁移尚未执行。

unit 只验证独立规则，不连接数据库、网络或文件服务；需要真实测试数据库或存储的测试归 integration。e2e 从公开应用入口运行到最终可下载文件，中间业务逻辑不替换；外部 Oracle、模型或云存储以边界模拟替代，报告明确标注这是离线端到端测试，不等同于真实外部联调。

阶段编号只帮助定位流程顺序，不决定底层测试放在哪一层。纯编码比较、日期边界或数字换算测试仍放 unit，接口连接与落库检查放 integration。

## 每个步骤的固定验收内容

每步必须写清输入、处理规则、预期输出、异常与恢复办法、测试场景、对应测试以及通过标准。预期输出独立于被测试的函数，不允许先执行当前程序，再把结果保存为标准答案。

| 步骤 | 正常结果必须证明什么 | 异常与重复执行必须证明什么 |
|---|---|---|
| 1 获取 PO | 来源、PO 身份、文件与下载结果对应 | 单条坏记录不拖垮可处理记录；整页或网络故障如实失败并可重试；重复扫描不意外重复导入 |
| 2 文件校验与保存 | 保存内容完整，文件与来源可追溯 | 空文件、损坏文件和大小限制有明确结果；重复上传保护的缺口作为独立缺陷显示 |
| 3 内容提取 | 原文件的行数、代码、数量、单位和日期与人工核实答案一致 | 多页和同名商品不丢行；缺字段或提取失败明确标注，不伪造完整成功 |
| 4 建立订单 | 元数据与所有商品行准确落库并保留原行身份 | 同一文档重跑不意外新增订单；中途失败不留下被误认为完成的结果 |
| 5 匹配与换算 | 正确商品关联到正确 PO 行；换算数量有已确认依据 | 未匹配、编码冲突、换算缺依据单独解释；数量、单位、商品或规则变化后不能复用不适用的旧数量 |
| 6 归组 | 同装船日、同所选港口归组；每个 PO 的行仍独立 | 不同日期或港口不错误合并；缺资料转人工；人工调整后的成员和统计一致 |
| 7 生成询价 | 使用真实系统模板，供应商、商品、数量、价格依据、来源和警告位置正确 | 合格行不因兄弟行问题全部丢失；警告行标黄；生成失败可追溯；重试不混淆询价版本 |
| 8 异常与人工修正 | 问题对应当前版本与当前行，统计和展示一致 | 修正后对应旧错误消失，其他真实问题保留；普通编辑、逐行修正和整单匹配不能产生不同口径 |

所有步骤共同检查订单 ID、PO 编号、来源文档和稳定行身份。匹配成功不等于没有警告；采购价没有命中装船日，只标记需要复核，不单独取消商品匹配或阻断询价。没有事实依据的商品包装、拆箱规则、价格和日期不得在测试或程序中猜测。

## 样本与预期结果

`fixtures/po_to_inquiry/` 中可提交的资料只包含明确标为合成的样本或已获授权的脱敏资料。每个 case 的 README 说明用途、来源类别、人工核对依据、覆盖步骤和限制；input 保存原始需求及必要主数据，expected 保存具体行结果、数量、问题代码和询价结果。

可公开的 source.pdf 是可选文件，仅在有合法脱敏原件或明确合成 PDF 时加入；没有原 PDF 的 case 不能宣称验证了提取准确性。样本生成可使用现有测试 helper，但正确预期不能调用被测匹配或换算逻辑计算。

真实受控样本继续由现有 `test-orders/` 加载，路径、授权与哈希在本地验收记录中说明。缺私有资料时明确 skip 并给原因，不计为通过。真实外部服务联调须明确启用并记录范围，不能因默认测试运行而访问生产数据库、调用模型、发邮件或发送供应商文件。

公共 fixture 创建一个测试自己的用户、港口、商品、规则和订单，不在模块间共享可变数据库状态。共用的资料生成放 fixture helper，不通过导入其他 `test_*.py` 文件复用。不要把所有场景塞进一个大 JSON 或一个大测试函数。

## 现有测试的复用与迁移

先为每个旧用例建立原 node ID、目标 node ID 和验收场景的对应清单，区分迁移、保留、新增和重复清理。参数化测试的每组输入也需可追溯。

已有 Oracle scan/import、port resolution、product matching、unit conversion、arrangement matching、group inquiry、order issue overview、orders API、template/workbook quality、PDF pipeline 和八阶段测试优先复用。一个文件混合多层测试时按测试实际依赖拆分，不靠文件名机械归类。

每个旧测试只能保留一个执行版本，不复制到新目录后让两份同时运行。通过 fixture 提取解决路径依赖，不能写只转发旧测试的包装文件制造新目录覆盖。无关 `section_*` 暂不迁移。

更新 `test_v2/README.md` 时移除过期的“896 个测试、0 失败”当前状态说法，历史数量若保留须明确日期。维护 `docs/testing/po_to_inquiry.md` 作为八阶段验收唯一入口；各类测试 README 只说明运行，不复制第二套标准。

## 已知缺陷的记录方式

当前已复现的错行写入、旧换算数量复用、匹配后旧异常污染不是目录整理可以修好的问题。本轮测试结构建设不暗中修改应用逻辑来让结果变绿。

已确认缺陷的最小反例需进入可运行的测试。应用尚未修复时，使用有明确问题编号和原因的 `xfail(strict=True)`：报告必须单独列出预期失败，不能计为业务通过；意外通过会让该项失败，要求移除过期标记并按正常回归测试保留。不允许用无理由 skip、宽泛捕获异常或改错预期掩盖缺陷。

未知的新失败是失败，不自动改成 xfail。框架交付可证明测试可运行、覆盖可追溯，但只要相关缺陷尚未修复，就不能声称 PO 流程整体通过。应用修复与后续历史数据刷新另行计划、验证和授权。

## 运行报告与验收门槛

默认命令继续从 `v3_backend/` 运行 `.venv/bin/python -m pytest`。新目录可按路径运行单步、某个测试层或完整 PO 链路，不为了每个小步骤重复执行全部后端测试。

测试报告输出到 `v3_backend/artifacts/test-results/`，不进入 Git。至少包含运行命令、源码版本、运行时间、通过、失败、跳过、预期失败数量及具体失败用例；JUnit XML 保留 node ID，验收清单把该 ID 对应到步骤与场景。该目录不得包含凭据或未经授权的客户资料。

目录迁移的验收不是“数量相同”：旧用例映射完整、默认收集无错误、没有重复执行、已有断言保持、相关测试运行结果一致、缺失样本仍如实跳过，才算通过。新场景数量单独记录。

运行顺序遵循工程经验：收集与单步测试、相关连接测试、完整 PO 链路、稳定候选一次本地完整回归。用户要求合并发布时，再按既有流程执行 CI；本轮不推送、合并、部署，不让纯文档提交触发重复全量测试。

## 分阶段交付边界

1. 确认书面设计，形成具体文件映射与可执行计划。
2. 建立目录、公共 fixture、样本规则和测试报告约定，并验证现有收集没有缺失。
3. 分批复用或迁移八阶段相关测试，加入已确认缺陷反例与缺失场景；每批独立验收。
4. 接通完整流程与失败恢复测试，核对实际生成的 Excel 内容，检查文档与运行命令。
5. 交付测试清单与结果，明确通过、未通过、需受控样本和待修应用缺陷，不能把“结构已建立”说成“业务全部正确”。

业务流程八阶段不变，旧测试入口保持兼容。没有独立的新后端、测试数据库服务或复杂测试平台；测试数据库与临时文件由现有 fixture 提供，需要 PostgreSQL 的专项测试继续使用现有受控测试机制。
