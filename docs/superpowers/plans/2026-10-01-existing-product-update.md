# Existing Product Update Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the approved five-stage “已有产品更新” workflow to the CruiseAgent workbench without creating a second backend upload pipeline.

**Architecture:** Build a dedicated frontend route that composes the existing product list, workbook export, workbench upload, validation, row review, commit, history and rollback APIs. Extend the workbook builder with a typed update scope, keep the existing backend authoritative, and extract only the small workbench UI primitives that would otherwise be duplicated.

**Tech Stack:** Next.js 16, React 19, TypeScript, shadcn/Radix UI, SheetJS, Vitest, existing FastAPI/SQLAlchemy workbench API.

**Spec:** `docs/superpowers/specs/2026-10-01-existing-product-update-design.md`

## Global Constraints

- No database migration or new product-write endpoint.
- No AI matching, approval flow, automatic pricing, image upload, or new master-data fields.
- Roles remain aligned with existing product-upload access: superadmin, admin, employee.
- Existing `/api/data-upload/workbench/*` validation and commit behavior remains authoritative.
- Use the current compact CruiseAgent design system and Chinese copy from the approved reference.
- Tests follow red-green-refactor; run one complete local frontend regression only after the stable candidate.

## Review Focus

- Selection across filter/page changes must not silently lose already selected products; Task 4 tests persistent ID-based selection.
- Empty selection or empty update scope must block moving forward; Task 4 reducer tests both guards.
- A workbook scoped to one price type must not carry the other type’s period rows; Task 2 tests purchase-only and selling-only exports.
- A server-classified create row must not be committable through this existing-product-only flow; Task 4 tests the blocking guard.
- Commit-time revision conflicts must preserve the review state and surface the server error; Task 5 tests the reducer/controller transition.
