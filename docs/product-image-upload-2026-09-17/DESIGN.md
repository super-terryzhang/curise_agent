# 产品图片上传工作台设计

日期：2026-09-17
状态：已确认，待实现

## 1. 目标与边界

用户从“工作台 → 产品图片上传”进入专用页面，直接选择或拖入多张图片。系统先把图片保存到临时批次并完成校验、匹配和最终图片顺序核对，只有用户确认后才写入正式产品图库。

本次替换新页面对 ZIP 的依赖，但保留旧 ZIP 后端接口，避免破坏已有调用。数据管理页不再展示重复的“批量图片”入口；单产品图库仍保留作为日常查看和维护入口。

## 2. 已确认的业务规则

1. 图片允许 JPG、JPEG、PNG、WebP，单张最大 5MB；文件必须能被 Pillow 实际解码。
2. 每个产品最多 30 张图片，第二步预检和最终提交都必须重新校验。
3. `Product.code` 不唯一，因此确认后的真实关联必须保存 `product_id`；文件名推断只能在当前筛选范围内作为辅助建议。
4. 未匹配、匹配歧义、图片损坏、格式不支持、文件过大和超出产品容量都是阻塞问题。
5. 用户必须通过“分配产品”“替换图片”或“排除”消除所有阻塞问题，才能进入最终核对。
6. 产品图片 `display_order == 0` 即主图；最终网格第一张同时代表主图和显示顺序第一位。
7. 成功写入必须幂等；失败行保留临时文件并允许单行重试，刷新后可恢复未完成批次。

## 3. 用户流程

### Step 1：选择图片

页面顶部提供国家、港口、产品搜索，用于缩小产品范围。用户可以把图片拖到具体产品行，也可以一次选择多个文件让系统在当前范围内按文件名建议匹配；直接拖到产品的图片保存明确的 `product_id`，不再二次猜测。

创建批次后每张图片独立上传，页面显示逐文件进度和失败重试。上传只写临时对象，不改变正式图库。

### Step 2：程序检查

服务端对每张图片执行真实解码、MIME/扩展名、大小、产品匹配和容量校验。界面默认只显示不通过项目，并为每项提供明确原因及“分配产品”“替换”“排除”操作；全部通过时直接允许继续。

容量按“当前正式图片数 + 本批次未排除图片数”计算。任何修正后服务器重新计算受影响产品，不能只在浏览器中隐藏错误。

### Step 3：核对主图与显示顺序

左侧是本批次涉及的产品列表及“现有 N 张 / 新增 N 张 / 最终 N 张”摘要，右侧是选中产品的最终图片网格。现有图片和新图片使用同一尺寸、同一排列规则；新图片带“新增”标识，第一张带“主图”标识。

拖动图片即可改变最终顺序；点击任意图片的“设为主图”会把它移动到第一位。所有操作只更新批次计划，顶部始终显示未保存变更，并提供“恢复默认顺序”；刷新页面后从服务器恢复同一计划。

默认顺序是：保留全部现有图片及其相对顺序，再按上传顺序追加新图片。用户没有操作时，现有主图不会被改变。

### Step 4：确认提交

确认页显示产品数、新增图片数、主图变化数、排序变化数和排除数。服务器提交前再次验证正式图片集合与容量；提交逐产品串行、逐行幂等，避免重复点击产生重复图片。

结果页区分成功、失败和排除。失败行保留 24 小时，可单独重试；批次列表允许恢复未完成批次并查看近期结果。

## 4. 页面与交互结构

- 专用路由：`/dashboard/workbench/image-upload`。
- 页面沿用当前工作台的日式 business 风格：统一字号、低饱和状态色、清晰表格/网格、无装饰性统计卡。
- 四步导航只表达当前位置与完成状态，不承担业务操作。
- Step 3 不使用“主图弹窗”和“排序弹窗”；主图、顺序和最终效果在同一网格完成。
- 拖拽之外提供键盘可达的“左移、右移、设为主图”，确保操作不依赖鼠标精度。

## 5. 后端设计

### 5.1 数据库迁移 0030

扩展 `v3_bulk_image_batches`：

- `source_type`：`zip` 或 `direct`，旧数据回填为 `zip`。
- `excluded_count`、`failed_count`：便于恢复页和结果页显示。

扩展 `v3_bulk_image_staging`：

- `storage_key`、`preview_storage_key`、`content_type`：逐图临时对象与预览。
- `issue_code`：稳定机器码；`error_message` 保留中文用户信息。
- `upload_order`、`decision`、`retry_count`、`committed_image_id`：顺序、排除、重试和幂等。

新增 `v3_bulk_image_product_plans`：

- `batch_id`、`product_id` 唯一。
- `expected_existing_image_ids`：创建/最后刷新计划时的正式图片集合，用于发现并发修改。
- `ordered_items`：`existing:<id>` 与 `staged:<id>` 的完整最终顺序。
- `updated_at`：排序计划恢复与审计。

### 5.2 新接口

- `POST /api/data/bulk-images/direct`：创建直接上传批次。
- `POST /api/data/bulk-images/{batch_id}/files`：逐张上传并校验，可携带明确 `product_id`。
- `GET /api/data/bulk-images/active`：恢复当前未完成批次。
- `GET /api/data/bulk-images`：分页读取本人近期批次。
- `PATCH /api/data/bulk-images/{batch_id}/rows/{row_id}`：分配产品或排除。
- `PUT /api/data/bulk-images/{batch_id}/plans/{product_id}`：保存完整最终顺序。
- `POST /api/data/bulk-images/{batch_id}/validate`：重新计算全部阻塞问题。
- `POST /api/data/bulk-images/{batch_id}/rows/{row_id}/retry`：重试单个提交失败行。

旧的 template、ZIP preview、batch get、commit 和 cancel 接口继续工作。新接口使用 `ProductUploader` 权限并继续执行批次所有权检查。

### 5.3 状态机

直接批次：`uploading → validating → preview_ready → processing → completed`，任一步可按规则进入 `cancelled` 或 `error`。行状态使用 `checking / ready / needs_attention / excluded / committed / committed_failed`，具体原因由 `issue_code` 表达。

提交时先锁定批次并校验计划，然后按产品处理。每个 staging 行用 `committed_image_id` 保证重复任务或重复重试不会创建第二张正式图片。

### 5.4 存储与清理

原图暂存在 `bulk-image-staging/{batch_id}/original/`，预览图在 `bulk-image-staging/{batch_id}/preview/`。成功行在正式图片和计划保存后清理临时对象；失败行保留到重试成功、用户取消或 GC 超过 24 小时。

现有每小时 GC 扩展为同时清理逐图临时对象。GCS `bulk-image-staging/` 48 小时生命周期继续作为最终兜底。

## 6. 前端设计

旧 `BulkImagesTab.tsx` 不继续扩张；新页面拆分为页面控制器、上传区、问题表、产品列表、最终图片网格、确认摘要和结果视图。API 客户端使用可测试的纯类型与请求函数，页面状态以服务器批次为事实来源。

文件上传控制并发数，单文件失败不阻断其他文件。页面加载时先读取 active batch；用户可以继续、取消或从历史新建批次，避免刷新后出现“后端说已有批次但页面什么都没有”的死锁。

## 7. 并发与异常

- Step 2 的通过只是预检，提交时必须重新检查容量、产品存在性和正式图片集合。
- 若其他用户在核对期间修改了同一产品图库，计划进入 `needs_attention` 并提示刷新最终顺序，不静默覆盖。
- 对象存储上传失败保持在当前行并允许重新选择/重传；正式写入失败记录中文原因并允许服务器端重试。
- 取消操作清理未提交临时对象，但不删除已经成功写入的正式图片。

## 8. 测试与发布标准

后端覆盖迁移、权限/所有权、真实解码、容量、匹配、排除、计划校验、主图/排序、幂等提交、单行重试、并发冲突和 GC。前端覆盖工作台入口、状态转换、问题修复门禁、最终顺序纯函数、active batch 恢复和 API 错误中文显示。

发布前运行后端专项与完整 pytest、架构检查，前端 Vitest、TypeScript 和生产构建。生产按“备份 → 0030 迁移 → 后端发布与健康核验 → 前端发布 → 权限/上传/校验/排序/提交/重试验收”执行，并更新生产核验与进度文档。
