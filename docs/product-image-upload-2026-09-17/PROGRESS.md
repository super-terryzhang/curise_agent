## 已确认现状

1. 工作台已有“产品图片上传”卡片，但仍指向通用数据管理页；没有专用图片工作台路由。
2. 旧流程是约 800 行的 ZIP 三步组件，刷新会丢失当前批次，且没有批次列表、恢复入口或逐行重试。
3. 产品编码在数据库中不唯一；可靠匹配必须保存 `product_id`，文件名推断只能作为受筛选范围约束的辅助匹配。
4. 旧预览只检查扩展名、大小、ZIP 路径和匹配；真实图片解码及每产品 30 张上限直到提交才失败。
5. 主图当前由 `display_order == 0` 表示；后端已有完整排序接口，但前端单产品图库没有接入拖拽排序。
6. 旧批次只保存一个 ZIP 对象；提交后删除 ZIP，因此失败行不能从服务器直接重试，也无法为刷新后的页面恢复逐图预览。
7. GCS/本地存储抽象支持逐文件上传、下载、删除和短期预览链接，5MB 单图低于 Cloud Run 请求限制，适合改成逐图暂存。
8. 工作台卡片不向财务角色展示，但旧图片接口使用包含财务角色的通用 Writer 权限；新工作台需要统一为产品上传者权限。
9. 当前 Alembic head 是 0029；CI 已覆盖后端 pytest、架构检查、前端 Vitest、TypeScript 和 Next.js build，但没有图片批量工作台前端测试。

## 当前设计决策（待确认）

- 推荐新增“直接逐图暂存”批次协议，并保留旧 ZIP API 兼容，不再让新页面依赖 ZIP。
- 第二步在正式写入前完成真实解码、格式/大小、产品匹配和容量校验；阻塞问题必须分配产品、替换文件或排除后才能继续。
- 第三步使用一个统一的最终图片网格：现有图片与待上传图片一起显示，第一张就是主图；拖动即调整最终顺序，点击“设为主图”等价于移动到第一位，所有变化在最终提交前都可重置。
- 提交时服务器再次校验产品容量和图片集合，逐行幂等写入；失败图片保留暂存文件供重试，成功图片清理暂存文件。
